## A. クレーム対応（実装タスク・優先）

### A-1. BPの毎月半分回復ができていない

**現状把握**

実装自体はリポジトリに存在している。

| 層 | 場所 | 内容 |
|---|---|---|
| GAS | `gas/Code.gs:2925`（`monthly_bp_recover` action） | 30日経過チェック → `回復量 = min(cap×50%, cap − 現在BP)` → `bp_last_reset_at` 更新 → `wallet_ledger` に記録 |
| API | `app/api/wallet/recover/route.ts` | GAS への proxy（adminKey 付与） |
| フロント | `app/top/page.tsx:366` | TOPページ表示時に fetch（失敗はサイレント無視） |

**「できていない」原因の候補（調査順）**

1. **本番GASに未デプロイ（最有力）**：`gas/Code.gs` はリポジトリ上のコピーで、本番の GAS Webアプリへは手動デプロイが必要。`monthly_bp_recover` が本番に反映されていなければ、フロントはサイレント失敗するため誰も気づかない。
   → 検証：本番GASに `action: "monthly_bp_recover"` を直接POSTしてレスポンスを確認する。
2. **plan 値がマップ外**：cap は `{34, 57, 114, 567, 1134}` / 5000系 `{500, 2000, 3000, 5000}` のハードコード。`applies` シートの `plan` 列がこれ以外の値だと `unknown_plan` で回復されない。
   → 検証：シートの `plan` 列の実値を確認する。
3. **TOPページを開かないと発火しない**：サーバー側の定期実行はなく、ユーザーが `/top` を訪問したときのみチェックされる。
4. **回復量0でもサイクルがリセットされる**：BPが cap 近くにあると回復量0のまま `bp_last_reset_at` が更新され、「回復されていない」と感じる（仕様通りだが体感と乖離）。
5. **group パラメータ**：/5000ユーザーは auth に `group` が入っていないと通常シートを検索して `not_found` になる可能性。

**追記（2026-07-10 aisalon点検で判明）**：姉妹リポジトリ aisalon では同じ `monthly_bp_recover` の capマップに**旧プラン値（30/50/100/500/1000）も含めて**おり、さらに全ユーザー一括回復の運用関数 `bulkBpRecovery()` を持つ。LIFAIOVのマップは新値（34/57/114/567/1134）のみなので、`plan` 列が旧値のユーザーは `unknown_plan` で回復されない可能性が高い。詳細は `docs/2026-07-10-aisalon-diff-report.md` §1-1。

**修正案（基本構造は変えない）**

- [ ] 本番GASのデプロイ状況を確認し、未反映なら `gas/Code.gs` を再デプロイする
- [ ] （aisalon式）capマップに旧プラン値 `30/50/100/500/1000` を追加し、`bulkBpRecovery()` を移植して未回復分を一括リカバリする
- [ ] GAS側で失敗理由（`unknown_plan` / `not_found` / `already_recovered`）をログシート等に記録し、原因を特定できるようにする
- [ ] `plan` 列の実値と cap マップの不一致があれば cap マップを実値に合わせる
- [ ] （検討）「/top訪問時のみ」で漏れるユーザーが問題なら、GASの時間主導トリガーで全 approved ユーザーを一括回復する関数を追加する（action の仕組みは変えず関数を足すだけ）
- [ ] （検討）回復した際にTOP画面へ「+N BP回復しました」の通知を出し、ユーザーに見える化する

## B. ユーザー質問への回答と改善案

### B-1. 「音楽を作成した後、やはり歌詞がおかしいと思って変更できないのか？」

**現状の仕様**

- 生成直後の結果画面には「表示用歌詞」の✏️インライン編集がある（`app/music2/page.tsx:1571-1624`）
- **ただし編集はブラウザ内の state のみで、保存されない**。履歴（GAS `music_history` / localStorage）には生成完了時の歌詞がそのまま残り、ページを離れると編集は消える
- 生成ログ（履歴）からは歌詞の閲覧・コピーのみで編集不可
- 音源そのもの（歌唱内容）は生成済みのため後から変更不可 → 歌い直しは再生成（BP消費）が必要

**改善案（基本構造を変えない）**

- [ ] **歌詞編集の永続化**：結果画面の「✅ 保存」時に `POST /api/music/history`（GAS `music_history_save` は jobId で upsert 済み）を呼んで lyrics を上書き保存する
- [ ] **履歴からの編集**：生成ログの各カードに「歌詞を編集」を追加し、同じ upsert APIを再利用する
- [ ] （中期）音源ごと作り直したい場合の「修正した歌詞で再生成」ボタン：既存の `/api/song/start` に手動歌詞を渡す形の拡張。BP消費が発生するため課金表示とセットで検討

### B-2. 「narasu代理申請でリンクを何曲も引っ張るのに一度ページを離れないといけない」

**現状の仕様**

- 申請フォーム（`app/narasu-agency/form/page.tsx`）の音源URLは手貼りのみ
- 自分の曲のURLは `/music2` の生成ログにあり、コピーのたびにフォームを離れる必要がある（下書きは sessionStorage 保存されるので消えはしないが手間）
- 一方、サーバーには `GET /api/music/history?userId=` で本人の生成履歴（title / audioUrl / downloadUrl / lyrics）を返すAPIが既にある

**改善案（既存APIの再利用で実現可能）**

- [ ] フォームの音源URL欄に **「🎵 自分の生成曲から選ぶ」ボタン＋選択モーダル** を追加
  - `/api/music/history` から一覧取得し、チェックで複数曲選択 → url / 曲名 / 歌詞をまとめて自動入力
  - ページ遷移なし・コピペ不要になる
- [ ] 手貼り入力は従来通り残す（外部音源用）。既存の曲名自動取得（resolve-title）とも共存
- 影響範囲：フォームページのみ。API・GASの変更は不要

## C. 7/13 打ち合わせ議題（実装保留・要意思決定）

### C-1. Music Boost の支払い方法とフォロー運用

**現状把握**

- プラン定義：`app/music-boost/page.tsx:45-56`（Starter $9〜Legend $1000）
- **EP払い**：`price × 100` EP（Starter = **900 EP**）。GAS `musicBoostSubscribe_`（`gas/Code.gs:10937`）でEP即時控除、`expires_at` = 30日後
- **クレカ払い**：Square checkout（`/api/square/create-checkout`）による都度決済。自動継続課金（サブスクリプション）は未実装
- **期限切れの自動処理はない**：`expires_at` を過ぎても自動で `canceled` にはならず、未払い者の追跡・楽曲削除は手動運用 → 運営の管理負荷が高い（今回の指摘の核心）

**打ち合わせで決めること**

1. ブーストの支払いを **クレカ一択** にするか（現状のコード上は `paymentMethod` パラメータで切替可能なので、UI からEPボタンを外すだけで対応できる）
2. 折衷案：**EPは最初の3ヶ月だけ → 4ヶ月目から自動課金**（Square Subscriptions API の導入検討が必要。カード情報の事前取得を含む）
3. **価格改定**：900 EP（Starter）は安すぎるとの意見 → EP換算レート（×100）またはプラン価格の見直し
4. EP払いを残す場合の管理コスト削減：GASの時間主導トリガーで `expires_at` 超過分を自動 `canceled` 化＋本人へ期限切れメール通知（手動追跡を廃止）

**技術メモ**

- クレカ一択化のみなら：`music-boost/page.tsx` のEP決済ボタン・確認モーダルの非表示化だけで完結（GAS変更不要）
- 自動課金は Square Subscriptions（または定期課金リンク）の新規統合が必要 → 工数中〜大
- 期限切れ自動処理は GAS 側に関数＋トリガー追加のみ → 工数小・効果大なのでどの案でも先行実装を推奨
