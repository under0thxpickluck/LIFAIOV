# BP貢献度オークション（マーケット内シンク）設計書

- 日付: 2026-07-24
- ステータス: ドラフト（ブレインストーミング合意 → 要ユーザーレビュー）
- 対象: LIFAI マーケット内に新設する「BP貢献度オークション（テスト版）」

---

## 1. 背景・目的

BPが慢性的にインフレし、AI生成機能などのBP建て単価が実質「紙くず化」している。
原因は **フォーセット（付与・毎月回復・アフィリエイトBP・ガチャ払い戻し）がシンク（消費先）を上回っていた**こと。
※ガチャの高RTP（払戻率125%＝BP印刷機化）は運用側で既に絞り込み済み。本機能は**既存の在庫BPを掃くシンク**として位置づける。

ゴール（ブレインストーミングで合意）:

1. **再循環させて熱狂を作る** — BPを気持ちよく大量投入させ、salon の熱量を上げる。
2. その裏で **ハウスエッジ（純減）を効かせ、総流通量を継続的に減らす**。
3. **運営の手出し現金ほぼゼロ** — 景品は現金・転売価値ゼロの「参加・発言の機会」に限定。
4. **偶然性を完全に排除** — 順位は純粋にBP貢献度のみで決定。くじ引き要素なし。
5. **確定リターン付き** — 投じたBPは全員に一定レートでEP還元（＝"損"が発生しない）。

> 位置づけ: 既存マーケット（C2C出品）の中に「オークション」区画を新設。まずは**小規模テスト1本**から。

## 2. 現状ロジック解析（実装ベース）

### 2.1 BPの出入り

| 区分 | 内容 | 実装箇所 |
|---|---|---|
| フォーセット | プラン購入付与（300〜12,000BP） | `planToGrant_` (gas/Code.gs:6506) |
| フォーセット | 毎月回復（上限 `BP_CAP_MAP` 300〜12,000） | Code.gs:2382 ほか |
| フォーセット | ガチャ払い戻し（BP→BP、※RTP絞り込み済み） | `gacha_spin` (Code.gs:3691) |
| シンク | AI生成消費（music_bgm 288 / note_full 300 等） | `app/lib/bp-config.ts` `BP_COSTS` |
| シンク | マーケット出品100 / ブースト200 | `bp-config.ts` |
| 現金流入 | BPパック購入（$5=500BP 〜 $50=10,000BP） | `BP_PACKS` (bp-config.ts) |

**重要**: BPは `BP_PACKS` で現金購入が可能。BPは純粋な無償ポイントではなく一部は現金対価で取得される。これが第11章の法務設計の前提。

### 2.2 BP残高操作の共通パターン（踏襲対象）

`deduct_bp` (Code.gs:2403) が模範実装:
- `adminKey` 検証 → `applies` シートで `login_id` 一致行を探索 → `bp_balance` 残高チェック → 減算 → `appendWalletLedger_` で記帳。
- 台帳スキーマ: `ts, kind, login_id, email, amount, memo`（`appendWalletLedger_` Code.gs:6458）。
- レスポンスは `json_({ ok, bp_balance })`。

### 2.3 EPミントの現状

- アフィリエイトEPは `epRateForPlan_` (Code.gs:6810) で**プラン別レート（500=3, 2000/3000=2.5, 5000=2 EP/円）**により「円建て価値保存」でミント。
- 本機能のEP還元は**それとは別系統の定数ミント**（第6.4章）。

### 2.4 ミニゲームのアーキテクチャ（踏襲対象）

rumble が完成度の高い雛形:
- Nextルート (`app/api/minigames/rumble/*`) は **薄いプロキシ**。`{ action, key, ... }` をGASにPOSTするだけ。
- シーズン制ランキング (`rumble_ranking` + `weekId`)、エントリー (`rumble_entry`)、日次トリガーを持つ。
- **本機能もこの構造をそのまま拡張**（新規発明を避ける）。

## 3. 機構（貢献度オークション）

### 3.1 方式: 確定EP還元 ＋ 貢献度ランキング（偶然性ゼロ）

純粋なAll-Pay抽選（外れれば喪失）ではなく、**「BP消費＝確定でEPに交換」＋「累積貢献額で上位が追加特典」**という構造にする。これにより賭博の構成要件（偶然性・賭金喪失）を外す。

- 各「セッション」は **1つ以上の特典ティア・各ティアの定員・開始/終了時刻** を持つ。
- ユーザーは **BPを投入（貢献）** する。投入した瞬間にBPが **即時消費** され、`wallet_ledger` に記帳される。
- 投入と同時に、**全員へ確定でEPを還元**（既定 1000BP → 1EP、第6.4章）。誰も"損"をしない。最悪でもBPを明示レートでEPに交換しただけ。
- ユーザーの **累積投入額 = スコア**。
- 終了時点のスコアで、**上位者が決定論的に特典ティアへ割り当てられる**（乱数一切なし）。

> シンクの本体: 投入BPは戻らない（EPに1000:1で交換されるのみ）。落選者を含む全参加者のBPが燃えるため、100万BP勢が本気で投入するほど総量が純減する。

### 3.2 特典はティア制（決定論的割り当て）

| ティア | 定員（テスト既定） | 特典 |
|---|---|---|
| Tier 1 | 上位5名 | **LIFAI新システム体験会の優先参加権 ＋ ベータテスター意見交換会 参加券** |
| Tier 2 | 6〜15位 | **ベータテスター意見交換会 参加券**（システム部門へ直接意見を上げられる） |

- 定員は運用（オンライン開催の席数）に応じて可変。裾野を広げると 6〜15位も投入を続けるためシンク効率が上がる。
- いずれも **現金化・転売不可の「参加・発言の機会」**。経済価値ほぼゼロ。

### 3.3 ソフトクローズ（駆け込み対策）

- 終了直前 `softclose_min` 分以内の投入で **いずれかのティア境界が変動**したら、終了時刻を `now + softclose_min` に延長。
- 「最後の数秒だけ全員が突っ込む」を防ぎ、熱量を持続させる。

### 3.4 投入ルール

- 投入額は `min_bid`（既定1,000BP）以上。以降 **1,000BP単位**（還元EPが整数で綺麗になる）。累積加算。
- 残高不足なら `insufficient_bp` を返し、消費・還元とも行わない（原子性を保証。GAS `LockService` 併用）。
- **テスト期間は1人あたり投入上限**を設定（露出を限定・独走を緩和）。
- 返金は原則なし（＝EPに交換済み）。**例外**: セッションが運営都合で中止された場合のみ、BP全額返還＋還元EPの取り消し（第9章）。

## 4. 公開・透明性設計

「見えること」が熱量の燃料であり、かつ**完全開示は法務上もプラス**（隠し仕様なし＝不当表示回避）。

| 項目 | 公開範囲 |
|---|---|
| ランキング表示 | **上位20〜30位まで**（Tier2ライン層まで見せる） |
| 見出し数値 | **各ティアの現在ボーダー（あと◯◯BPで◯位ティア）** |
| 他人のスコア | 順位＋表示名（ハンドル）＋バンド帯のみ（正確なBP額は伏せる） |
| 自分のスコア | **常に自分にだけフル表示**（順位＋正確な累積額＋還元済みEP） |
| ルール | 投入BPは戻らない／1000BP=1EP確定還元／各ティア特典／乱数なし・投入額順 を常時明示 |
| 残り時間 | カウントダウン＋ソフトクローズ発動表示 |

一番BPを燃やすのはボーダー付近の層。ここを可視化しつつ、各whaleの正確額は伏せて戦意喪失とプライバシーに配慮する。

## 5. 景品設計（現金・転売価値ゼロの機会）

景品選定3原則: **①運営の現金コストほぼゼロ ②本質的に希少 ③毎月回せる ④転売・換金不可**。

採用（テスト第1回）:
- **LIFAI新システム体験会への優先参加権**
- **ベータテスター オンライン意見交換会 参加券**（システム部門へ直接フィードバック）

いずれもオンライン開催＝運営の時間のみ・非経済的な参加/発言の機会。BP最大保有者を**製品の当事者（ベータテスター＆擁護者）**に転換できる戦略的メリットもある。

将来の景品候補（同条件を満たすもの）: 主宰1on1枠、narasu代行「最優先枠」、限定称号ロール、殿堂掲載。
**非採用**: 物販・EPそのもの・現金価値のあるもの（手出し／現金負債／転売リスク）。

## 6. データモデル（GAS シート新設）

### 6.1 `auction_sessions`

| 列 | 説明 |
|---|---|
| session_id | UUID |
| title | 表示名 |
| tiers_json | ティア定義 `[{tier:1, capacity:5, prize:"..."}, ...]` |
| currency | `BP`（固定） |
| min_bid / bid_step | 最小投入・投入単位（既定1000/1000） |
| ep_return_per_bp | EP還元レート（既定 0.001＝1000BP→1EP） |
| per_user_cap | テスト期間の1人上限 |
| start_at / end_at | 開催期間 |
| softclose_min | ソフトクローズ延長分 |
| status | `scheduled` / `live` / `closed` / `cancelled` |
| refunded_at | 中止返還済みタイムスタンプ（二重返還防止） |
| created_at | |

### 6.2 `auction_bids`（append-only）

| 列 | 説明 |
|---|---|
| bid_id | UUID |
| session_id | |
| login_id / display_name | |
| amount | 投入BP（正） |
| ep_returned | この投入で還元したEP |
| ts | |

- スコア = 当該 session_id の amount 合計。高速化が必要なら `auction_standings`（session×login累積）を集約キャッシュとして併設（将来拡張）。

### 6.3 `wallet_ledger`（既存流用）

- 投入消費: `kind="auction_bid"`, `amount = -投入BP`, `memo=セッション名`。
- EP還元: `kind="auction_ep_return"`, `amount = +還元EP`, `memo=セッション名`（BP台帳とは別にEP増減も記帳）。
- 中止返還: `kind="auction_refund_bp"`（+BP）／`kind="auction_ep_clawback"`（-EP）。

### 6.4 EP還元ミント

- **定数レート**（`ep_return_per_bp`、既定 0.001）で `applies.ep_balance` に加算。`epRateForPlan_` のプラン別ミントとは**別系統**。
- 投入と同一トランザクションで処理（BP減算とEP加算を原子的に）。
- ※EP換金機能は現状未実装＝**繰延負債**。換金解禁時に顕在化する点を経理上把握する。

## 7. GAS アクション / API ルート

Nextルートは薄いプロキシ（rumble踏襲）。配置は `app/api/market/auction/*`。

| GAS action | 呼び元 | 内容 |
|---|---|---|
| `auction_list` | 一覧 | live/scheduled 一覧 |
| `auction_detail` | 詳細 | セッション情報＋ランキング（上位帯＋各ティアボーダー＋自分の順位/累積/還元EP） |
| `auction_bid` | 投入 | 上限/残高チェック→BP減算＋EP還元（原子的）→`auction_bids`追記→`wallet_ledger`記帳→ソフトクローズ判定→新スコア返却 |
| `auction_ranking` | 観戦 | 公開ランキング（上位20＋各ティアボーダー） |
| `auction_close` | トリガー | 終了判定→ティア割り当て確定→`status=closed`→当選フラグ（rumble日次トリガー踏襲） |
| `admin_auction_create` | 管理 | セッション作成 |
| `admin_auction_cancel` | 管理 | 中止＋全投入返還＋還元EP取り消し |
| `admin_auction_fulfill` | 管理 | 特典付与済みマーク（体験会/意見交換会の招待送付の運用記録） |

- 認証: minigames同様、Nextルートがサーバー側で `key`（＋必要なら `adminKey`）を保持し `loginId` を渡す。
- 原子性: `LockService` でセッション単位ロック。

## 9. 台帳・監査・整合性

- 全BP/EP移動は `wallet_ledger` に残り、既存の管理画面集計と整合。
- `auction_bids` に投入と還元EPを二重記録し台帳とクロスチェック可能。
- 中止時のみ BP全額返還＋還元EP取り消し。`refunded_at` で二重返還防止。

## 10. 経済効果の試算

- 投入BPは戻らない（EPに1000:1交換）ため、**1セッションで純減するBP = 全参加者の投入総和**。
- EP還元による現金負債 = 投入総和 × `ep_return_per_bp` × EP換金価値。
  - 例（1EP=¥0.5、レート1000:1）: **投入100万BP → 還元1,000EP → 現金負債¥500**。
  - 現在の全流通（例 約376万BP）を全量掃いても **現金負債は約¥1,882**（＝BP破壊はほぼ無償）。
- レートを100:1（1万BP→100EP）に上げると負債は10倍。**`ep_return_per_bp` がそのまま現金コストを決める**。
- 実数は管理画面の現行BP集計と突き合わせ、`min_bid`／`per_user_cap`／開催頻度を調整する。

## 11. リスク・法務（設計で構造的に低減済み）

**本設計は賭博の構成要件を構造的に外している**:

| 賭博の要件 | 本設計 |
|---|---|
| 偶然性 | **なし**（順位は純粋にBP投入額で決定・乱数ゼロ） |
| 財物の喪失 | **なし**（投入BPは全員に確定でEP還元＝交換であり喪失でない） |
| 経済価値のある景品 | **なし**（景品は転売・換金不可の参加/発言の機会＝価額ほぼ¥0） |

→ 「賭博」ではなく **「BP消費キャンペーン＋貢献度に応じた招待」** として整理できる。景表法（景品類の価額規制）も、景品が非経済的なため影響は小さい。

**透明性ガード（実装必須）**:
1. 事前の完全開示＋同意チェック（投入BPは戻らない／1000BP=1EP確定還元／各ティア特典／乱数なし・投入額順）。
2. 全員に確定EP還元（対価性の担保）。
3. 景品は非換金・非譲渡の機会のみ。
4. ライブ全開示（ランキング・ボーダー・ルール）。
5. 全BP/EP移動を監査可能に記帳。中止時は全額返還。
6. approved会員限定＋テスト/β明示＋1人あたり投入上限。

**残存リスク・正直な但し書き**: 筆者は弁護士ではない。BPが現金購入可能（`BP_PACKS`）な点は残存要素であり、**公開スケール前には専門家レビューを推奨**。テストは小規模・会員限定・上限付きのため露出は限定的。
